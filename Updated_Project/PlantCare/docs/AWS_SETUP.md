# AWS setup and integration sequence

No account resources or credentials were created during this implementation. Use a team-owned AWS account and one selected region. Static lint and local SDK shape tests are not deployment acceptance.

1. Keep the existing Cognito user pool and app client for operator APIs. The only public data route is `GET /api/demo/telemetry`, which returns the latest live plant condition and sensor readings. Static dashboard files are public. All operator API routes still require a JWT.
2. Obtain the region's IoT Data-ATS endpoint. Install AWS CLI and SAM CLI, configure authorized deployment credentials, and run `sam build`. The custom Makefile copies only the runtime allowlist and pinned Python dependencies.
3. Before an approved AWS update, compare the proposed change set with the deployed stack. Check that Cognito issuer/audience settings, device policies, queues, and the History table are retained and that only the three dashboard asset routes and the new telemetry route target the public Demo function. Confirm that the single live plant is intended for public display. Keep existing deployment parameters, including BackendGeneration, for this dashboard-only update.
4. Create separate certificates/keys for sensor, display, simulated sensor and simulated display. Attach only the corresponding policy generated by the stack; do not attach a wildcard policy. Client IDs are `team3-sensor`, `team3-display`, `team3-sim-sensor`, `team3-sim-display`. Attach certificates to the corresponding Things if using a Thing registry. Keep private keys out of Git, reports, screenshots and ZIPs.
5. Use a simulator and the protected operator API to verify mode filtering, history, and command/event journals. Open the public dashboard without a token and verify that it shows only the live plant, with an unavailable state when fresh readings are absent. Live soil percentage appears only after calibration.
6. In AWS acceptance testing, confirm an anonymous GET succeeds for demo telemetry, returns only the documented fields, and rejects query parameters. Verify that anonymous and wrong-issuer/audience calls fail on the operator routes and that other methods on the demo route are rejected. Confirm the simulation certificate cannot access live IoT topics or client IDs.
7. Test queue retries/outbox recovery, receipt vs source times, deliberate duplicates and out-of-order messages, Lambda restarts, blocked publication, dead-letter alarms, absent telemetry and heartbeat delays. Check actual wall-clock display/dashboard stale behavior, not just a test counter.
8. Integrate the original PlantFace GUI using its bridge. Run measured calibration and pump bench acceptance before generating a qualified live configuration. Deploy matching `config_id` and `calibration_id` to firmware and profile.

## Privileged profile reload

Set `LIVE_QUEUE` and `SIM_QUEUE` to the stack's queue URLs in the operator shell. Use IAM permission to send only to the intended queue. Edit the fixed `profiles/live.json` or `profiles/simulated.json`, increment `profile_revision`, then run `python -m tools.reload_profile live` (or `simulated`). No path argument is accepted. The worker validates and journals the new profile, refuses an active transaction/pending control/cooldown, and disarms on a permitted reload while preserving unresolved faults. Confirm the revision via `/api/state`. Device-affecting changes also require regenerated/flashed firmware with matching IDs.

## Operations

Watch both DLQs and Lambda error/age metrics. The template's DLQ alarms have no notification destination; configure the team's chosen alarm destination in the account. Investigate before redriving old commands: expiry and boot checks must remain enabled. Do not clear fault markers or delete durable state to force a demo through. Explicit backend restart/redeploy increments `BackendGeneration`; active or uncertain transactions fault, otherwise the system disarms conservatively.
